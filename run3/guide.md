# SOC / CSIRT初動調査演習 ファシリテータガイド

> **演習担当者専用**  
> 本資料は進行、軽い解答確認、軌道修正、評価、全体解説、振り返りに使用する。受講者には `question.md`、ネットワーク構成図、`training.pcap`、その時点までの状況付与カード、固定フォーマットの初動調査メモのみを提示する。

## 1. 演習の目的

SOC / CSIRT配属直後の初任者が、通信証跡と状況付与から、次の初動能力を身につけることを目的とする。

- 確認済み事実と推測を分離する。
- PCAPで確認できること・できないことを理解する。
- 追加確認ログや関係者確認を具体化する。
- 攻撃・影響の流れを時系列で整理する。
- 証跡保全と影響拡大抑制を両立した初動案を作る。
- SOC / CSIRT内で適切に共有・エスカレーションする。

## 2. 想定対象者

- SOCまたはCSIRTに配属されたばかりの初任者。
- ネットワーク・セキュリティの基礎知識はある。
- PCAP解析やインシデント対応経験は少ない。
- 高度なマルウェア解析、詳細フォレンジック、経営・法務・広報判断は主対象としない。

## 3. 演習方式

状況付与を5段階で提示する机上訓練。各段階で受講者に、確認できた事実、推測、未確認事項、PCAPで確認できる内容、PCAPだけでは分からない内容、追加確認、初動対応、共有・エスカレーションを整理させる。

PCAPは「答え探し」ではなく、状況付与の通信面の裏付けである。軽い解答確認では模範解答をすべて開示せず、次の状況付与に進むための最低限の認識をそろえる。


## 7. 軽い解答確認の進め方（共通）

各状況付与後の5分前後の確認は、次の順序で行う。

1. **受講者に30〜60秒で回答を共有させる。** 「一番重要な確認済み事実」「まだ分からないこと」「次に確認したいもの」の3点だけでもよい。
2. **事実と推測を分離する。** 「それはPCAPまたはカードのどの情報で確認できますか」と尋ねる。
3. **PCAPで分かること・分からないことを確認する。** 認証、端末操作、ファイル操作を通信だけで断定していないか確認する。
4. **対象外へ広がった議論を戻す。** 広報・法務・経営判断・詳細マルウェア解析ではなく、SOC / CSIRT初動へ戻す。
5. **次の状況付与に必要な認識だけそろえる。** 後続の事実や模範解答は開示しない。

ファシリテータは「正しい攻撃名」を言わせるのではなく、回答の根拠と不確実性を言語化させる。

## 8. INJ-01 進行ガイド

### 期待するアクション

- UTM-VPN-01の役割と公開IPを構成図・ネットワーク定義から確認する。
- 外部送信元、宛先、TCP/443、通信方向、頻度を整理する。
- `external-probe-01` と `external-baseline-01` の相対的な頻度差に気付く。
- VPN認証ログ、設定変更履歴、正規保守記録を追加確認として挙げる。
- SOC / CSIRT内に「通常外通信、認証・侵入未確認」と共有する。

### 軽い解答確認で確認すること

- 通信の存在と認証成功を混同していないか。
- 「外部IPだから悪性」と決めつけていないか。
- PCAPで見える情報を具体的に説明できるか。

### 受講者が迷った場合の補足

- 第1段階：「公開側のどの資産への通信ですか」と構成図に戻す。
- 第2段階：「同じ宛先への別の外部通信と、回数・まとまり方を比べてください」と促す。
- 第3段階：「認証成否を確認するなら、PCAP以外の何のログが必要ですか」と問う。

### 軌道修正

「攻撃者がログインした」と断定した場合は、「認証装置の成功・失敗判定はどこで確認しますか」と問い、VPNログへ戻す。

### 直接教えてはいけない情報

- 認証成功・失敗の答え。
- VPN侵害、脆弱性悪用、認証情報窃取。
- 後続の内部通信の送信元端末。

### ディスカッションで扱う問い

- 通常外と評価するには、単一通信以外に何と比較するか。
- 正規保守の可能性をどう除外・確認するか。
- この段階でログ保全を始める理由は何か。

### 解説時に強調する点

外部通信増加は「調査開始の根拠」であって「侵入成功の証明」ではない。

## 9. INJ-02 進行ガイド

### 期待するアクション

- IT-PC-01からAD-SRV-01、FILE-SRV-01、ACC-PC-03、DEV-PC-07等への通信を整理する。
- VLAN40から複数セグメントへ通信が広がっていることを示す。
- Kerberos / LDAP / SMB / RDP / TCP 135を、サービス候補として認識する。
- 正常比較のGA-PC-01通信と比べる。
- AD認証ログ、Windowsイベント、EDR、IT作業記録を追加確認に挙げる。

### 軽い解答確認で確認すること

- 「横展開成功」と断定していないか。
- AD / File Shareの資産役割を説明できるか。
- 正規IT管理作業の可能性も考慮しているか。

### 受講者が迷った場合の補足

- 「192.168.40.1はどの部門・端末ですか」。
- 「宛先は同じVLANだけですか、複数VLANですか」。
- 「ログオン成功を確認するには、どのログが必要ですか」。

### 軌道修正

ツール名やコマンドに議論が寄ったら、「いま観測できているのはどのIP・ポートへの通信ですか」とPCAP事実へ戻す。

### 直接教えてはいけない情報

- IT-PC-01の侵害確定。
- ログオン成功、認証情報窃取。
- コマンド・プロセス・攻撃ツールの実行。

### ディスカッションで扱う問い

- IT管理端末からの通信は、なぜ正常・不審の両方の可能性があるか。
- 調査優先端末を選ぶ根拠は何か。
- 「隔離候補」と「侵害確定」の違いは何か。

### 解説時に強調する点

ポート・通信先は調査仮説を作る材料であり、端末上の行為を直接示す証拠ではない。

## 10. INJ-03 進行ガイド

### 期待するアクション

- 複数部門からFILE-SRV-01へのSMB/445集中を整理する。
- 利用者問い合わせとPCAP事実を別の証拠として扱う。
- FILE-SRV-01監査ログ、ファイル変更履歴、バックアップを追加確認に挙げる。
- 情報窃取・暗号化を断定しない。

### 軽い解答確認で確認すること

- 「SMB通信＝ファイル窃取／暗号化」としていないか。
- どの部門から通信が集中しているか説明できるか。
- 業務影響の範囲を追加確認事項として具体化できているか。

### 受講者が迷った場合の補足

- 「共通の宛先になっているサーバーはどれですか」。
- 「利用者の『開けない』という報告は、原因まで証明していますか」。
- 「ファイル操作内容を確認できるログはどこにありますか」。

### 軌道修正

情報漏えい・暗号化確定の議論になったら、「PCAPからファイルの中身・状態は確認できますか」と問い、監査ログ・ファイルシステム調査へ戻す。

### 直接教えてはいけない情報

- ファイル閲覧・コピー・変更。
- 情報窃取、暗号化、マルウェア実行。
- 原因と侵害範囲。

### ディスカッションで扱う問い

- 「ユーザ報告」と「ネットワーク証跡」はどう相互補完するか。
- バックアップ確認を初動で始める理由は何か。
- 共有サービスのアクセス制限は、どの情報をそろえて判断すべきか。

### 解説時に強調する点

影響報告は重要だが、原因をPCAPに押し付けない。異なる証跡を相関させて仮説を検証する。

## 11. INJ-04 進行ガイド

### 期待するアクション

- AD / File Share周辺の継続、再試行、一部リセットを確認する。
- 業務影響が複数部門に広がっていることから、重大度・優先度を上げる。
- ログ保全と隔離候補を同時に整理する。
- IT-PC-01等の隔離、VPN制限、認証情報変更等を「上位判断が必要な候補」として示す。
- SOC / CSIRT上位者へ、事実・未確認事項・判断依頼を分けてエスカレーションする。

### 軽い解答確認で確認すること

- 対応が証跡を破壊しないか。
- 「すべて停止」「すべて初期化」に飛躍していないか。
- エスカレーションの根拠が複数の観測事実に基づいているか。

### 受講者が迷った場合の補足

- 「いま消えると困る証拠は何ですか」。
- 「どの端末・サービスを優先調査候補にしますか。なぜですか」。
- 「上位者に何を決めてもらう必要がありますか」。

### 軌道修正

復旧、広報、法務へ脱線したら、「初動担当者として、証跡保全・影響抑制・追加確認・上位判断依頼の4点に戻してください」と整理する。

### 直接教えてはいけない情報

- 感染端末、攻撃成功、情報窃取、認証成功、マルウェア・暗号化の確定。
- 業務影響の根本原因。

### ディスカッションで扱う問い

- 端末隔離を決めるには、何を根拠にするか。
- VPN接続制限と業務影響をどう比較するか。
- 証跡保全を優先しながら影響拡大を抑えるにはどうするか。

### 解説時に強調する点

重大度を上げることと、技術原因を断定することは別。エスカレーションは不確実性を含んだまま実施してよい。

## 12. INJ-05 進行ガイド

### 期待するアクション

- INJ-01〜04の通信事実を時系列で一枚の初動調査メモに統合する。
- 事実、推測、未確認事項を明示する。
- 追加ログを優先順位付きで示す。
- 初動対応案とエスカレーションを「実施済み／候補／判断依頼」に分ける。
- 原因を無理に一つに決めない。

### 軽い解答確認で確認すること

- PCAPにない事実を「確認済み」にしていないか。
- 読み手が「次に何を確認すべきか」を理解できるか。
- エスカレーション対象と判断理由が明確か。

### 受講者が迷った場合の補足

- 「確認済み事実だけを5行で書くと何ですか」。
- 「その横に、未確認事項を対応させてください」。
- 「次の担当者が最初に開くログを3つ選んでください」。

### 軌道修正

原因当てゲームになった場合、「このメモを次のシフトへ渡したとき、事実と仮説を誤解なく再確認できますか」と問い、引継ぎ品質へ戻す。

### 直接教えてはいけない情報

軽い確認の段階では、`answer.md` の完全な模範メモや原報告書上の最終評価を先に提示しない。

### ディスカッションで扱う問い

- 良い初動メモは「何が分からないか」をどう書くべきか。
- エスカレーション文で断定を避けながら緊急度を伝えるにはどうするか。
- 追加ログが取得できない場合、次に何を代替証跡として使うか。

### 解説時に強調する点

初動報告の品質は、原因を当てたかではなく、事実・不確実性・次アクションが明確かで評価する。

## 13. 直接教えてはいけない情報の全体ルール

各状況付与の軽い解答確認では、後続状況のネタバレに加え、次を直接答えとして与えない。

- VPN / AD / SMB / RDP認証成功。
- 侵害端末の確定。
- 認証情報窃取。
- コマンド・プロセス・攻撃ツール・マルウェア実行。
- ファイル閲覧・コピー・変更・暗号化。
- 情報窃取。
- 攻撃成功、最終侵害範囲、攻撃者の意図。
- 詳細な攻撃手順、exploit payload、CVE悪用リクエスト。

全体解説でも、これらを**PCAPの事実として**説明してはいけない。原報告書由来の事実に触れる場合は、「原報告書で確認・評価された事項」と「本演習PCAPから確認できる事項」を明示的に分ける。

## 14. 評価観点

| 評価項目 | 達成の目安 | 要支援の例 |
|---|---|---|
| 確認できた事実の整理 | IP、方向、ポート、状況付与事実を具体的に記載 | 「攻撃された」等の抽象断定だけ |
| 推測と断定の分離 | 「可能性」「未確認」を明記 | 通信だけで侵害・認証成功を断定 |
| PCAP証跡の提示 | 対象通信・比較通信を示せる | 単一パケットだけで結論 |
| PCAP限界の理解 | 認証、端末、ファイル操作は別証跡と説明 | PCAPですべて分かると考える |
| 追加確認事項 | ログ名と確認目的が具体的 | 「ログを見る」だけで対象不明 |
| 初動対応案 | 保全と封じ込め候補を両立 | 証跡保全なしの全停止・初期化 |
| エスカレーション | 事実・未確認・判断依頼を分ける | 攻撃名だけを伝える |
| 軽い確認での修正 | 指摘後に表現・仮説を修正できる | 断定に固執する |
| 初動調査メモ | 時系列と根拠が読みやすい | 事実・推測が混在し次アクション不明 |

評価は「正解通信を全部見つけた数」だけで決めない。特に初任者には、断定の回避、追加確認の具体性、エスカレーションの説明力を重視する。

## 15. 初任者がつまずきやすい点

- ポート番号から実際のアプリケーション操作まで推測してしまう。
- SYN / ACK / RST等のTCP挙動を「認証成功・失敗」と読み替えてしまう。
- IT管理端末からの通信を、正常か悪性かの二択で即断する。
- SMB通信量とファイル操作内容を混同する。
- 利用者報告を原因確定の証拠として扱う。
- 重大度を上げるために「ランサムウェア確定」等の強い断定が必要だと考える。
- 封じ込めを「電源断・初期化」と同義に考える。
- 追加確認事項を列挙するだけで、何を確認したいかを書けない。

## 16. 振り返りで確認する点

振り返りでは、受講者に次の観点を言語化させる。

- どの場面で「断定したくなった」か。その根拠は十分だったか。
- PCAPから確認できた事実のうち、最も判断に役立ったものは何か。
- PCAPだけでは分からないと気付いた事項は何か。
- 現場なら最初に取りに行くログは何か。なぜか。
- 証跡保全と封じ込めの両立で難しかった点は何か。
- SOC / CSIRT上位者へ、どの段階で何をエスカレーションするか。
- 自組織で不足しているログ・台帳・連絡手順がないか。

## 17. ファシリテータ運営チェック

### 開始前

- `training.pcap` が受講者環境のWireshark等で正常に開けることを確認する。
- ネットワーク構成図のIP・ホスト名が `network.json` と一致することを確認する。
- `cards.pptx` の各カードが順序通り提示でき、後続カードが見えない状態にする。
- 初動調査メモの固定フォーマットが `question.md` の提出項目を満たしているか確認する。
- ファシリテータ間で、「侵害・認証・暗号化等はPCAPで断定しない」という共通ルールを共有する。

### 演習中

- 受講者がPCAP探索だけに没頭していないかを見る。
- 軽い解答確認は、答え合わせではなく認識合わせに留める。
- 後続状況付与の内容を匂わせない。
- 議論が高度なフォレンジック・攻撃手順・経営判断へ移ったら初動調査へ戻す。
- グループ間で進捗差が大きい場合、答えではなく「確認対象の役割」「事実と推測の境界」をヒントにする。

### 全体解説

- `answer.md` を用い、原報告書の要点と演習上の仮定を明確に分ける。
- F-001〜F-023の通信証拠と、NF-001〜NF-010の非PCAP事項を対応づける。
- 受講者の良い表現例として、「確認」「可能性」「未確認」を区別した回答を取り上げる。
- 強い断定があった場合は、誤りを責めるのではなく、どの追加証拠で検証できるかへつなげる。

## 18. 人間レビューが必要な点

1. **拡張時間の整合:** `design.xlsx` の拡張時列を合算すると4時間を超えるため、固定条件の4時間上限と運用版の正式時間を統一する。
2. **組織用語:** Shimada Laboratoryで実際に使用するSOC / CSIRTの役職名、エスカレーション経路、隔離権限と整合させる。
3. **ログ名称:** UTM/VPN、AD、EDR、File Shareの実製品名を使う場合は、受講者がアクセスできる範囲と矛盾しないようにする。
4. **統合PCAPの説明:** `training.pcap` は複数観測点相当の通信を1ファイルに統合した演習用証跡である。実環境の単一SPAN/TAPで同様に見えるとは限らない点を担当者間で共有する。
5. **難易度:** 初任者が2〜4時間内で、正常比較と不審通信を区別できるか事前試行する。
6. **PCAP表示:** 利用予定Wiresharkバージョンで、TCP/88等の表示が期待通りか確認し、ポート番号とアプリケーションの断定を混同させない。
7. **安全性:** 実在IP・ドメイン、認証情報、実攻撃可能なpayload等が追加資料に混入していないことを最終確認する。
