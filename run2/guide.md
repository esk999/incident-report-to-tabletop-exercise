# SOC / CSIRT 初動調査・通信証跡整理演習 ファシリテータガイド

> **演習担当者専用**
>
> 本資料は、状況付与の提示、軽い解答確認、軌道修正、全体解説、振り返りのために使用する。受講者へ事前配布しないこと。

## 1. 演習の目的

SOC / CSIRT配属直後の初任者が、状況付与と `training.pcap` をもとに、次を実践できるようにする。

- 確認できた事実を整理する。
- 推測・仮説と断定を分ける。
- PCAPで確認できる通信事実を示す。
- PCAPだけでは分からない事項を把握する。
- 追加で確認すべきログ・情報を整理する。
- 初動対応案を検討する。
- SOC / CSIRT内での共有・エスカレーション判断を行う。

PCAPは答え探しの中心教材ではなく、状況付与で提示された事実を通信レベルで裏付ける補助証跡として扱う。

---

## 2. 想定対象者

- SOCまたはCSIRTに配属されたばかりの初任者。
- ネットワーク・セキュリティの基礎知識はある。
- PCAP解析やインシデント対応の経験は少ない。

主対象ではないもの：高度なマルウェア解析者、詳細フォレンジック担当者、経験豊富なSOCアナリスト。

---

## 3. 演習方式

- 状況付与を段階的に提示する机上訓練。
- 受講者は各状況付与時点で、固定フォーマットの初動調査メモへ記録する。
- 利用できる資料は、ネットワーク構成図、`training.pcap`、その時点までに提示された状況付与カード、初動調査メモのみ。
- 各状況付与後に短い「軽い解答確認・軌道修正」を行う。
- 軽い確認では模範解答をすべて開示しない。
- 後続状況付与のネタバレは避ける。
- 最終段階で初動報告案を統合し、全体解説・振り返りへ進む。

---

## 4. 演習全体の流れ

1. 演習説明
2. 状況付与1 → 受講者検討 → 軽い確認
3. 状況付与2 → 受講者検討 → 軽い確認
4. 状況付与3 → 受講者検討 → 軽い確認
5. 状況付与4 → 受講者検討 → 軽い確認
6. 状況付与5 → 受講者検討 → 軽い確認
7. 最終整理
8. 全体解説
9. 振り返り

状況付与は、**外部入口の兆候 → 内部サービスへの通信 → ファイル共有周辺の通信増加 → 利用者影響申告 → 初動報告**という教育上の流れになっている。ただし、この全体像を受講者へ最初から示さない。

## 8. 軽い解答確認の基本進行

各状況付与後の確認は、次の順で行う。

1. **回答を短く共有させる**
   - 1グループ30〜60秒程度で、「確認できた事実」「未確認事項」「次に見るもの」を一つずつ言わせる。
2. **事実と推測を確認する**
   - 「それは状況付与の事実ですか、PCAPの事実ですか、仮説ですか」と問い返す。
3. **PCAPで分かること/分からないことを確認する**
   - 通信の存在から認証・実行・ファイル操作へ飛躍していないか確認する。
4. **対象外へ広がっていないか確認する**
   - 広報、法務、経営判断、長期復旧、高度解析へ進んだ場合は初動調査へ戻す。
5. **次へ進むための最低限の認識をそろえる**
   - すべての答えを開示せず、次の状況付与に必要な前提だけそろえる。
6. **後続のネタバレをしない**
   - 「次はファイルサーバに…」等、次のカードの内容を予告しない。

### 軽い確認で使える共通質問

- 「今、確認済みと書けるものは何ですか。」
- 「その結論はPCAPのどの情報で支えられますか。」
- 「PCAPだけで分からない部分はどこですか。」
- 「その判断に必要な追加ログは何ですか。」
- 「初動報告に書くなら、どの確度の表現にしますか。」

## 9. 状況付与1の進行

### 期待するアクション

- 外部送信元とUTM/VPN公開側の通信を確認する。
- TCP/443通信の存在、時刻、方向、回数を整理する。
- 比較用の低頻度通信と比較する。
- 認証成功や侵入成功を断定しない。
- UTM/VPN認証ログ、管理ログ、保守予定、許可送信元、設定情報、ログ保全を追加確認として挙げる。

### 軽い解答確認で確認する内容

- 外部→UTM/VPNという通信方向を捉えているか。
- 同一外部送信元からの通信が短時間に集中していることを確認しているか。
- 「VPN認証成功」をPCAP事実として扱っていないか。
- TCP/443通信自体は比較側にも存在するため、頻度や送信元・文脈を見る必要を理解しているか。

### 議論が脱線した場合の軌道修正

- 「外部から何宛の通信が見えますか。」
- 「認証の成否は、どのログなら確認できますか。」
- 脆弱性の具体的悪用方法へ進んだら、「本演習では攻撃手順ではなく、防御側の観測事実を整理します」と戻す。

### 受講者が迷った場合の補足

答えを教えず、次の範囲で問い返す。

- 「送信元と宛先を一つずつ確認してみてください。」
- 「同じ宛先への別送信元の通信はありますか。」
- 「回数や時間的な集中に違いはありますか。」

### 直接教えてはいけない情報

- VPN認証成功。
- 認証情報窃取。
- 脆弱性悪用成功。
- 攻撃者の意図。
- 内部侵入成功。
- 後続で内部サービスへの通信が出ること。

### ディスカッションで扱う問い

- 通信の存在と認証成功は何が違うか。
- 保守通信と不審通信を比較するには、PCAP以外に何が必要か。
- どのログを最優先で保全するか。

## 10. 状況付与2の進行

### 期待するアクション

- AD-SRV-01、FILE-SRV-01、複数VLAN端末への通信を資産役割と合わせて整理する。
- DNS、TCP/88、TCP/389、TCP/445を確認する。
- 内部探索・水平展開は「可能性」として表現する。
- ADログ、ファイルサーバログ、ファイアウォール/UTMログ、EDR/端末ログを追加確認として挙げる。

### 軽い解答確認で確認する内容

- ネットワーク構成図を使って通信先の役割を確認しているか。
- KerberosやLDAP通信の存在と、認証成功・権限取得を分けているか。
- 複数VLANへのTCP/445と水平展開成功を同一視していないか。
- 重要サービスへの接続増加を共有対象として整理しているか。

### 軌道修正

- 「通信先は何のサーバですか。」
- 「TCP/88や389が見えることから言えるのはどこまでですか。」
- 「成功を確定するには何の証跡が足りませんか。」

### 受講者が迷った場合の補足

- ネットワーク構成図のサーバ一覧・セグメント一覧を見るよう促す。
- 「1つの宛先だけでなく、どの範囲へ通信が広がっているか」を確認させる。

### 直接教えてはいけない情報

- AD認証成功。
- 管理者権限取得。
- 水平展開成功。
- 端末上でのコマンド実行。
- 特定端末の侵害。
- 後続でSMB集中・利用者影響が出ること。

### ディスカッションで扱う問い

- プロトコルの存在とアプリケーション側の結果をどう分けるか。
- 複数セグメントへの通信が見えたとき、追加でどのログを突合するか。
- どの段階で上位者へ早期共有するか。

## 11. 状況付与3の進行

### 期待するアクション

- DEV-PC-03→FILE-SRV-01のSMB通信集中を確認する。
- GA-PC-02→FILE-SRV-01の比較用SMB通信と比較する。
- 通信頻度・時系列・方向を整理する。
- ファイル操作・窃取・暗号化を断定しない。
- FILE-SRV-01監査ログ、対象端末ログ、平常時ベースライン、バックアップ状態を追加確認として挙げる。

### 軽い解答確認で確認する内容

- 「SMBがある」ではなく、「どの送信元からどの程度集中しているか」を見ているか。
- SMB通信から特定ファイル操作を断定していないか。
- 比較用SMBも存在することを認識しているか。
- ファイルサーバ監査ログが必要と理解しているか。

### 軌道修正

- 「SMB通信とファイルコピーは同じ事実ですか。」
- 「ファイル名、操作結果、アカウントを確認するには何が必要ですか。」
- 窃取・暗号化の議論に飛んだら、追加証跡へ戻す。

### 受講者が迷った場合の補足

- 「同じFILE-SRV-01へ接続する別端末の通信と比較してください。」
- 「短時間に集中しているか、長時間に分散しているかを見てください。」

### 直接教えてはいけない情報

- ファイル閲覧・コピー・削除。
- 情報窃取。
- 暗号化実行。
- マルウェア実行。
- DEV-PC-03が侵害端末であるという断定。
- 後続の利用者申告。

### ディスカッションで扱う問い

- SMB通信量の増加から何を仮説にできるか。
- 平常時比較がなぜ必要か。
- ファイルサーバログをどの優先度で保全するか。

## 12. 状況付与4の進行

### 期待するアクション

- 利用者申告を「申告された事実」として記録する。
- 原因・暗号化・マルウェアを未確認に置く。
- GA-PC-01/DEV-PC-01とFILE-SRV-01、DEV-PC-03とGA-PC-01の通信を確認する。
- ログ保全、影響範囲確認、バックアップ保全、必要な隔離・通信制限の検討を挙げる。
- 上位者へのエスカレーションを検討する。

### 軽い解答確認で確認する内容

- 利用者申告と技術的な原因確定を分けているか。
- 暗号化・感染をPCAP事実としていないか。
- 封じ込めと証跡保全の両方を考えているか。
- 複数部署への影響という重大性を認識しているか。

### 軌道修正

- 「『ファイルが開けない』は何を証明していますか。」
- 「原因を断定せず、今すぐできる初動は何ですか。」
- 復旧・再構築や広報判断へ進んだら、「今はSOC/CSIRT初動調査の範囲です」と戻す。

### 受講者が迷った場合の補足

- 「利用者申告、PCAP、ホスト側調査の3列に分けてみてください。」
- 「証拠を失わずに影響拡大を抑えるには、何を保全してから何を判断しますか。」

### 直接教えてはいけない情報

- ランサムウェア感染の断定。
- 暗号化実行の断定。
- 原因端末の断定。
- 攻撃成功。
- 情報窃取。
- 後続の外部HTTPS通信。

### ディスカッションで扱う問い

- 業務影響申告があるとき、確度が低くても何をエスカレーションするか。
- 証跡保全と封じ込めが衝突した場合、何を考慮するか。
- どの資産のログを優先して保全するか。

## 13. 状況付与5の進行

### 期待するアクション

- INJ-01〜04までの事実と、DEV-PC-03→外部ホストHTTPS通信を時系列で統合する。
- SALES-PC-01→自組織DMZ Webの比較用HTTPSも確認し、HTTPSそのものを悪性と決めつけない。
- 「確認済み」「仮説」「未確認」に分けた初動報告を作る。
- 追加確認の優先順位を付ける。
- 証跡保全、封じ込め候補、継続監視、上位者共有を整理する。

### 軽い解答確認で確認する内容

- 初動報告の文言に断定飛躍がないか。
- 外部HTTPSからC2・窃取を断定していないか。
- すべての状況付与を「ランサムウェア確定」という一文に潰していないか。
- 不足証跡と追加ログ取得状況を説明できるか。
- エスカレーション理由が、観測事実と業務影響に基づいているか。

### 軌道修正

- 「その文言は、どの証拠で確認済みですか。」
- 「仮説として書くなら、どう表現しますか。」
- 「PCAPだけでは確認できない部分を列挙してください。」

### 受講者が迷った場合の補足

- 初動調査メモを「確認済み / 推測 / 未確認 / 追加確認 / 対応」の5つに一度並べ直させる。
- 「外部宛HTTPSの宛先は自組織DMZか、演習用外部ホストか」をネットワーク定義と照合させる。

### 直接教えてはいけない情報

軽い確認中は次を断定的に教えない。

- 侵入経路の正解。
- 侵害端末・原因端末。
- 攻撃成功。
- VPN/AD認証成功。
- 情報窃取。
- マルウェア実行。
- 暗号化実行。
- C2成立。

これらは全体解説でも「PCAPで確定した」とは説明しない。

### ディスカッションで扱う問い

- 初動報告で「未確認」を明示することにどんな価値があるか。
- エスカレーションに必要なのは「攻撃成功の確定」か、それとも「重大な兆候と業務影響」か。
- 次に1つだけログを得られるなら何を選び、なぜか。

## 14. `training.pcap` のファシリテータ向け確認ポイント

`training.pcap` は1,654パケット、約119分のキャプチャである。演習担当者は事前に少なくとも次を確認する。

| 状況付与 | 不審側として設計した通信 | 比較側として設計した通信 | 観察させたい差 |
|---|---|---|---|
| INJ-01 | external-probe-01 → UTM/VPN TCP/443、接続開始約24回 | external-maintenance-01 → UTM/VPN TCP/443、約5回 | 短時間集中と低頻度 |
| INJ-02 | UTM/VPN関連 → AD/FILE/複数VLAN | GA-PC-01 → AD DNS | 宛先範囲・プロトコルの広がり |
| INJ-03 | DEV-PC-03 → FILE-SRV-01 SMB、約38接続開始 | GA-PC-02 → FILE-SRV-01 SMB、約8回 | SMBの集中度 |
| INJ-04 | GA-PC-01/DEV-PC-01 → FILE-SRV-01、DEV-PC-03 → GA-PC-01 TCP445 | IT-PC-01 → AD DNS | 利用者申告前後の関連通信と通常DNS |
| INJ-05 | DEV-PC-03 → external-observer-01 HTTPS、約9接続開始 | SALES-PC-01 → 自組織WEB-SRV-01 HTTPS、約13回を分散 | 外部宛先の役割・時系列 |

### PCAP説明で避けること

- 特定のWireshark表示フィルタを「答え」として配る。
- TCP/443をVPN認証成功として扱う。
- TCP/88をKerberos認証成功として扱う。
- TCP/445/SMBをファイルコピー・暗号化の証明として扱う。
- 外部HTTPSをC2・情報窃取の証明として扱う。

## 15. 受講者が迷った場合の補足方針

### レベル1：観点だけ返す

- 「送信元、宛先、時刻、プロトコル、回数の順で見てください。」
- 「ネットワーク構成図上で、そのIPが何の役割か確認してください。」
- 「比較できる別の通信がないか探してください。」

### レベル2：切り分けの枠を与える

- 「状況付与の事実 / PCAPの事実 / 仮説 / 未確認に分けてください。」
- 「認証結果はネットワークだけでなく、装置・サーバ側ログが必要ではないでしょうか。」

### レベル3：次へ進めない場合の最小補助

- 「通信の存在は確認できています。成功・実行結果までは確認できていません。この2つを分けてください。」

レベル3でも、後続状況付与や具体的なfindingの答えは教えない。

## 16. 議論が脱線した場合の共通軌道修正

### 攻撃手順の再現へ進んだ場合

「本演習では攻撃の再現ではなく、防御側が今持っている証跡から何を判断できるかを扱います。」

### 高度なマルウェア解析へ進んだ場合

「マルウェア本体の解析は対象外です。初動担当として、どの証跡を保全・追加取得するかへ戻してください。」

### 広報・法務・経営判断へ進んだ場合

「詳細判断は対象外です。SOC / CSIRTから上位者・関係部署へ何を共有すべきか、という範囲で整理してください。」

### 長期復旧へ進んだ場合

「復旧設計の詳細ではなく、今この時点の証跡保全、影響範囲確認、被害拡大防止へ戻してください。」

### 一つの仮説に固執した場合

「その仮説を支持する観測事実と、反証・未確認の情報を分けて挙げてください。」

## 17. 直接教えてはいけない情報の一覧

状況付与の進行中、ファシリテータは次を答えとして直接与えない。

- 後続状況付与の内容・提示順序。
- `answer_key.json` のfinding IDや `traffic_id`。
- どの通信を設計上「suspicious」と分類したか。
- VPN認証成功・侵入成功。
- VPN脆弱性悪用成功・認証情報窃取。
- AD認証成功・管理者権限取得。
- 水平展開成功。
- 特定端末が侵害端末・原因端末であること。
- ファイル閲覧・コピー・削除・窃取。
- マルウェア実行・暗号化実行。
- 外部HTTPSのC2成立。
- 攻撃者の意図。
- 答えに直結するWiresharkフィルタ。

## 18. 全体解説で開示してよい情報

全状況付与終了後は、次を開示してよい。

- 元公開報告書から抽出した「VPN起点が疑われた重大インシデント」という要点。
- それをUTM/VPN、AD、ファイルサーバ、クライアントへ写像した演習設計。
- `training.pcap` で意図的に配置した不審側・比較側の通信。
- F-001〜F-018のPCAP finding。
- それぞれについて「PCAPで確認できる事実」と「PCAPだけでは断定できない事項」。
- 追加ログの優先順位と初動対応の考え方。

ただし、解説時も「演習上の意図した攻撃ストーリー」と「PCAPが証明した事実」を区別する。

## 19. 解説時に強調する点

1. **確度の表現**
   - 「確認した」「可能性がある」「未確認」を使い分ける。
2. **PCAPの限界**
   - 通信の存在は見えても、装置・OS・アプリケーションの結果は別証跡が必要。
3. **比較の重要性**
   - TCP/443、DNS、SMB、HTTPSは通常業務でも発生し得る。頻度、宛先、時系列、役割を比較する。
4. **利用者申告の扱い**
   - 申告は重要な状況事実だが、技術的原因の確定ではない。
5. **追加確認の具体性**
   - 「ログを見る」ではなく、VPN認証ログ、ADセキュリティログ、ファイル監査ログ、EDR等まで具体化する。
6. **初動と証跡保全**
   - 被害拡大防止だけでなく、後続調査に必要な証跡を失わないことも考える。
7. **エスカレーション**
   - 攻撃成功が完全確定するまで待つのではなく、重大な兆候・業務影響・未確認事項を確度付きで共有する。

## 20. 評価観点

評価は、単一の「正解文」を再現できたかではなく、初動調査としての整理品質を見る。

| 評価観点 | 良好な状態 | 要支援の状態 |
|---|---|---|
| 確認できた事実 | 状況付与事実とPCAP事実を分けて具体的に記載 | 印象や仮説を事実として記載 |
| 推測と断定 | 「可能性」「未確認」を適切に使用 | 攻撃成功・侵害・暗号化等を根拠なく断定 |
| PCAPの裏付け | 送信元・宛先・時刻・方向・プロトコル・回数を示す | 「怪しい通信がある」だけで具体性がない |
| PCAPの限界 | 認証、実行、ファイル操作等は追加証跡が必要と理解 | PCAPだけでホスト事象を確定 |
| 追加確認 | VPN/AD/FILE/EDR等を目的付きで挙げる | 「ログを確認」のみ、目的が不明 |
| 初動対応 | 保全、影響範囲、監視、封じ込め、記録をバランスよく検討 | いきなり復旧・再構築、または何もしない |
| エスカレーション | 重大性と確度を説明して共有判断 | 完全確定まで共有しない、または断定情報を過剰共有 |
| 軽い確認後の修正 | 指摘を受けて事実/仮説を修正できる | 最初の仮説に固執する |
| 初動調査メモ | 読み手が時系列・確度・次の行動を把握できる | 情報が混在し、判断理由が追えない |

### 評価時の注意

- 追加確認項目の順序に唯一の正解を置かない。
- 組織固有の手順が未提示であるため、隔離方法などの細部より、根拠・証跡保全・影響考慮を評価する。
- 受講者が正しく「分からない」と判断できたことを積極的に評価する。

## 21. 初任者がつまずきやすい点

### 1. ポート番号から結果まで推測する

例：TCP/88を見て「AD認証成功」とする。

**支援**：「プロトコル通信の存在」と「サーバが返した最終的な認証結果」を分ける。

### 2. SMB通信をそのまま窃取・暗号化と捉える

**支援**：通常SMB比較通信を見せ、ファイル監査ログが必要な理由を考えさせる。

### 3. 利用者申告を技術的な原因確定と捉える

**支援**：「申告内容は事実、原因は未確認」という2列に分ける。

### 4. 攻撃シナリオらしさに引っ張られる

**支援**：各主張の根拠を「状況付与」「PCAP」「追加ログ待ち」のどれかに分類させる。

### 5. 追加確認が抽象的

**支援**：「何を判断するために、どのログの何を見るか」を言わせる。

### 6. すぐに長期復旧へ進む

**支援**：初動段階での証跡保全、影響範囲確認、共有へ戻す。

### 7. エスカレーションを「確定後」と考える

**支援**：重大な兆候と業務影響がある場合、未確認事項を明示したうえで共有できることを確認する。

## 22. 振り返りで確認する点

振り返りでは、模範解答の再確認だけでなく、受講者がどこで判断に迷ったかを言語化させる。

### 事実と推測

- どの場面で断定しそうになったか。
- 「未確認」と書くことに抵抗があったか。
- 何を根拠に仮説を更新したか。

### PCAP

- PCAPで確認しやすかった事実は何か。
- PCAPでは確認できず、追加ログが必要だと感じたものは何か。
- 比較通信が判断にどう役立ったか。

### 初動対応

- ログ保全と封じ込めの優先順位をどう考えたか。
- 影響範囲を確認するために何を追加で欲しいか。
- 現場の実運用では、そのログを本当に取得できるか。

### 共有・エスカレーション

- どの時点で上位者へ共有すべきと判断したか。
- 「確認済み」「可能性」「未確認」を報告文にどう反映したか。
- 現場のエスカレーション経路と演習の想定に差があるか。

## 24. 人間レビューが必要な点

1. **組織固有手順との整合**
   - ログ取得依頼先、隔離権限、エスカレーション経路は組織により異なるため要確認。
2. **UTM/VPNの演習上の見え方**
   - VPN割当アドレスを追加せず、各VLANゲートウェイIPへSNATされた形でPCAPに表現している。実運用イメージとの乖離が教育上許容できるか確認する。
3. **短縮/拡張版のカード時間表示**
   - カードは標準版時間固定。運営上の説明方法を事前に決める。
4. **難易度**
   - INJ-01の外部接続集中、INJ-03のSMB集中が対象者にとって明瞭すぎる/難しすぎる場合は、人間がPCAP再設計の要否を判断する。
5. **評価基準**
   - 本ガイドは定性的評価。正式な採点制度が必要な場合は、組織の教育制度に合わせて別途定義する。
