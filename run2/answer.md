# SOC / CSIRT 初動調査・通信証跡整理演習 模範解答

> **演習担当者専用**
>
> 本資料は受講者への事前配布を想定しない。状況付与の進行中は、各時点で必要な範囲だけを用いて軽い解答確認・軌道修正を行い、後続状況付与の内容や結論を先に示さないこと。

## 1. 演習の学習目標

本演習では、SOC / CSIRT配属直後の初任者が、状況付与と `training.pcap` を用いて次の事項を整理できることを目標とする。

- 攻撃の流れを、観測事実と仮説を分けて時系列で整理する。
- 初動調査で確認すべき事項を優先順位付きで挙げる。
- PCAPから直接確認できる通信事実と、PCAPだけでは断定できない事項を切り分ける。
- 認証、端末上の実行、ファイル操作、情報窃取、暗号化などについて、追加ログやホスト調査が必要であることを理解する。
- 初動段階の証跡保全、被害拡大防止、継続監視、共有・エスカレーションを検討する。
- SOC / CSIRT内で報告するとき、情報の確度を「確認済み」「推測・仮説」「未確認」に分けて表現する。

本演習は、高度なマルウェア解析、詳細フォレンジック、攻撃手順の再現、広報・法務・経営判断の詳細を主題としない。

## 2. 攻撃シナリオの概要

### シナリオ全体の要約

`design.xlsx` で `report_fact` として整理された元の公開インシデント報告書の要点は、**VPN装置の脆弱性を悪用した侵入が疑われ、複数端末・サーバのデータが利用不能となる重大インシデントへ発展した**という点である。

本演習では、この要点をそのまま攻撃手順として再現せず、自組織のネットワーク構成へ次のように写像している。

- 公開側の入口を `UTM-VPN-01` に写像する。
- 内部の重要サービスとして `AD-SRV-01` と `FILE-SRV-01` を扱う。
- 複数のクライアントセグメントへの通信、FILE-SRV-01周辺のSMB通信、利用者からの業務影響申告を段階的に提示する。
- 最終段階では、外部宛HTTPS通信も含む全体時系列を整理させる。

**演習上の仮定**として、`training.pcap` には上記を考察するための通信を配置している。これらは「攻撃成功」をPCAPで証明するものではない。特に、VPN認証成功、AD認証成功、権限取得、ファイル操作、マルウェア実行、暗号化実行、情報窃取、C2成立、侵害端末の確定はPCAPだけでは断定させない。

| INJ-02 | 内部重要サービス・複数セグメントへの接続 | 内部探索・水平展開の**可能性**を仮説として表現し、認証・権限取得・実行成功を断定しない。 |

| INJ-05 | 全体時系列の統合・初動報告 | 確認済み事実、仮説、未確認事項を確度付きでまとめ、追加確認とエスカレーションを判断する。 |

### PCAPで確認できる範囲

`training.pcap` から直接確認する対象は、主として次の通信メタデータである。

- 通信時刻・時系列
- 送信元IPアドレス
- 宛先IPアドレス
- 通信方向
- プロトコル
- 宛先ポート
- 通信の有無
- 接続回数・継続時間・通信量の傾向
- 同一宛先に対する平常寄りの比較通信と、短時間に集中した通信との差

`training.pcap` は1,654パケットで、キャプチャ時間は約119分である。18件の `traffic_plan` はすべてPCAP内に対応通信があり、`answer_key.json` の18件のPCAP findingはすべて対応する `traffic_id` を参照している。

### PCAPだけでは断定できない範囲

次の事項はPCAPだけで「確認済み」としない。

- VPN認証の成否
- VPN装置の脆弱性悪用の成否
- 認証情報窃取
- AD認証の成否
- 管理者権限取得
- 端末上で実行されたコマンドやプロセス
- 水平展開の成功
- 特定ファイルの閲覧・コピー・変更・削除
- 情報窃取
- マルウェア実行
- ファイル暗号化実行
- 外部宛HTTPS通信のC2成立
- 攻撃者の意図
- 原因端末・侵害端末・侵害範囲の確定
- 利用者から申告されたファイル利用不可の技術的原因

### 解説時に強調する点

1. **通信があることと、その通信で何かが成功したことは別である。**
2. **プロトコル名やポート番号は調査の方向を示すが、認証結果やホスト上の実行結果を保証しない。**
3. **「攻撃らしい流れ」が見えても、初動報告では証拠ごとの確度を維持する。**
4. **PCAPで足りない情報を明確にし、追加でどのログ・調査が必要かを挙げられること自体が重要な成果である。**
5. **利用者申告は重要な事実だが、原因の断定とは分ける。**

## 3. 攻撃シナリオと状況付与の対応

演習担当者は、次の「意図したストーリー」と「証拠として言えること」を混同しない。

| 段階 | 演習上の意図 | PCAPで言えること | PCAPだけでは言えないこと |
|---|---|---|---|
| 入口 | VPN入口へ通常と異なる外部接続が増える | 外部IP→UTM/VPN TCP/443の存在・頻度 | VPN認証成功、侵入成功、脆弱性悪用 |
| 内部接続 | 重要サービスと複数VLANへの接続が続く | DNS/Kerberos/LDAP/SMB/TCP445の存在と範囲 | AD認証成功、権限取得、水平展開成功 |
| ファイル共有 | FILE-SRV-01へのSMBが短時間に集中 | SMB通信の頻度・方向・量の傾向 | ファイル閲覧、コピー、削除、窃取 |
| 影響兆候 | 複数部署から利用不可申告が出る | 申告前後に関連端末とFILE-SRV-01の通信が存在 | 暗号化、マルウェア、原因端末、破損原因 |
| 初動報告 | 全体を確度付きで統合する | 外部・内部・SMB・外部宛HTTPSの時系列 | C2成立、情報窃取、侵害範囲の確定 |

## 4. 状況付与1 模範解答：VPN装置への外部接続の兆候

### この時点で確認できる事実

- 状況付与では、通常の保守予定がない時間帯に、同一外部送信元からUTM(VPN)宛の接続が増えていると提示される。
- `training.pcap` には `198.51.100.23` から `192.0.2.11` へのTCP/443通信が短時間に複数回存在する。
- 比較用として `203.0.113.50` から `192.0.2.11` へのTCP/443通信も存在するが、頻度は低い。
- 実PCAPでは、疑わしい側はTCP接続開始が24回程度、比較側は5回程度であり、頻度差を確認できる。

### 推測にとどめるべきこと

- 通常の保守通信とは異なる可能性がある。
- 不審な外部接続の可能性がある。
- VPNを入口とした事象につながる可能性がある。

これらは仮説であり、「侵入成功」とは表現しない。

### まだ断定できないこと

- VPN認証が成功したか。
- VPNアカウントが悪用されたか。
- VPN装置の脆弱性が悪用されたか。
- 認証情報が窃取されたか。
- 外部送信元が攻撃者か。
- 内部ネットワークへ侵入したか。

### PCAPで確認すべき通信

| finding | traffic_id | 観測対象 | 確認観点 |
|---|---|---|---|
| F-001 | TR-INJ01-001 | 198.51.100.23 → 192.0.2.11 TCP/443 | 時刻、方向、回数、送信元の集中 |
| F-002 | TR-CMP01-001 | 203.0.113.50 → 192.0.2.11 TCP/443 | 低頻度の比較通信との違い |

### 追加確認が必要な情報

- UTM/VPN認証ログ
- 接続元別の認証成功・失敗記録
- 対象アカウントと認証時刻
- UTM/VPN管理ログ・設定変更履歴
- UTM/VPNのバージョンと脆弱性管理状況
- 許可送信元設定
- 保守予定・保守元の情報
- 関連ログの保全状況と保存期間

### 軽い解答確認で受講者に確認するポイント

- 外部IP、UTM/VPN公開側IP、TCP/443、通信回数の差を事実として挙げられているか。
- 「通信がある」から「認証成功」「侵入成功」へ飛躍していないか。
- 追加確認としてVPN認証ログや管理ログを挙げられているか。
- 比較通信があるため、TCP/443通信そのものだけでは異常を断定できないと理解しているか。

### 議論が脱線した場合の戻し方

- 「PCAPで今、直接見えている送信元と宛先は何ですか。」
- 「認証成功を確認するなら、PCAP以外に何が必要ですか。」
- 攻撃者像、具体的な脆弱性悪用手順、侵入後の動作へ進みすぎたら、まず外部接続の観測事実へ戻す。

### 次の状況付与に進むために揃えておきたい認識

- UTM/VPNへの外部接続増加は確認できる。
- 認証成功・侵入成功は未確認である。
- UTM/VPN側のログ保全・確認が必要である。
- 現時点でもSOC / CSIRT内で「通常と異なる外部接続がある」という事実は共有対象になり得る。

## 5. 状況付与2 模範解答：内部サービスへの広範な接続

### この時点で確認できる事実

- UTM/VPN関連の内部側送信元から、AD-SRV-01およびFILE-SRV-01への複数種類の通信が観測される。
- 複数のクライアントセグメントに対するTCP/445通信も観測される。
- 比較用として、GA-PC-01からAD-SRV-01への通常寄りのDNS通信が継続して存在する。
- 実PCAPにおける主な接続開始・要求回数の目安は次の通り。
  - UTM/VPN VLAN100側 → AD-SRV-01 DNS: 12要求程度
  - UTM/VPN VLAN100側 → AD-SRV-01 TCP/88: 8接続開始程度
  - UTM/VPN VLAN100側 → AD-SRV-01 TCP/389: 7接続開始程度
  - UTM/VPN VLAN100側 → FILE-SRV-01 TCP/445: 8接続開始程度
  - VLAN10/20/50側ゲートウェイ → 各代表端末 TCP/445: 各6接続開始程度
  - GA-PC-01 → AD-SRV-01 DNS: 比較用に30要求程度を広い時間範囲へ配置

### 推測にとどめるべきこと

- 内部サービスの探索や、水平展開を試みている可能性。
- 認証・名前解決・ディレクトリサービス・ファイル共有に関係する通信を順に行っている可能性。
- 複数セグメントへ通信範囲が広がっているため、影響範囲確認を急ぐ必要がある可能性。

### まだ断定できないこと

- AD認証が成功したか。
- どのアカウントが使用されたか。
- 管理者権限を取得したか。
- TCP/445接続先へのログオンや共有アクセスが成功したか。
- 端末上でコマンドやツールが実行されたか。
- 水平展開が成功したか。
- いずれかの端末が侵害済みか。

### PCAPで確認すべき通信

| finding | traffic_id | 観測対象 |
|---|---|---|
| F-003 | TR-INJ02-001 | 192.168.100.254 → AD-SRV-01 DNS/53 |
| F-004 | TR-INJ02-002 | 192.168.100.254 → AD-SRV-01 TCP/88 |
| F-005 | TR-INJ02-003 | 192.168.100.254 → AD-SRV-01 TCP/389 |
| F-006 | TR-INJ02-004 | 192.168.100.254 → FILE-SRV-01 TCP/445 |
| F-007 | TR-INJ02-005 | 192.168.10.254 → GA-PC-01 TCP/445 |
| F-008 | TR-INJ02-006 | 192.168.20.254 → ACC-PC-01 TCP/445 |
| F-009 | TR-INJ02-007 | 192.168.50.254 → DEV-PC-01 TCP/445 |
| F-010 | TR-CMP02-001 | GA-PC-01 → AD-SRV-01 DNS/53（比較用） |

### 追加確認が必要な情報

- ADセキュリティログ
- Kerberos関連ログ
- アカウント変更履歴
- グループメンバーシップ変更履歴
- 接続先端末のOSイベントログ、EDRログ
- FILE-SRV-01のサーバログ・監査ログ
- UTM/ファイアウォールの通信ログ
- 平常時のセグメント間通信の基準

### 軽い解答確認で受講者に確認するポイント

- ネットワーク構成図からAD-SRV-01、FILE-SRV-01、各VLAN端末の役割を確認できているか。
- DNS、TCP/88、TCP/389、TCP/445の**存在**を事実として整理しているか。
- 「Kerberosがある=認証成功」「TCP/445がある=水平展開成功」としていないか。
- 通信範囲の広がりをSOC / CSIRT内の共有対象として認識できているか。

### 議論が脱線した場合の戻し方

- 「通信先はネットワーク構成図上で何の役割ですか。」
- 「PCAPで分かるのは接続の存在です。ログオン成功はどこで確認しますか。」
- 攻撃ツール名や具体的な侵入手順の推測に偏った場合は、必要な追加ログと観測事実へ戻す。

### 次の状況付与に進むために揃えておきたい認識

- 内部重要サービスと複数セグメントへの通信は確認できる。
- 内部探索・水平展開は合理的な仮説になり得るが、成功は未確認である。
- AD・端末・サーバ側ログの突合が必要である。

## 6. 状況付与3 模範解答：ファイル共有周辺の通信増加

### この時点で確認できる事実

- DEV-PC-03からFILE-SRV-01へのSMB通信が短時間に集中している。
- GA-PC-02からFILE-SRV-01への比較用SMB通信も存在するが、低頻度で長い時間範囲に分散している。
- 実PCAPでは、DEV-PC-03側はTCP接続開始が38回程度、GA-PC-02側は8回程度であり、頻度・集中度に差がある。

### 推測にとどめるべきこと

- DEV-PC-03からFILE-SRV-01への通信が通常業務と異なる可能性。
- ファイル共有を利用した何らかの大量処理が行われている可能性。
- それまでの通信と関連している可能性。

### まだ断定できないこと

- どのアカウントで接続したか。
- 特定ファイルを閲覧したか。
- ファイルをコピー、変更、削除したか。
- 情報窃取が行われたか。
- ファイル暗号化が行われたか。
- DEV-PC-03が侵害端末か、原因端末か。

### PCAPで確認すべき通信

| finding | traffic_id | 観測対象 | 比較ポイント |
|---|---|---|---|
| F-011 | TR-INJ03-001 | DEV-PC-03 → FILE-SRV-01 SMB/445 | 短時間の集中、回数、方向 |
| F-012 | TR-CMP03-001 | GA-PC-02 → FILE-SRV-01 SMB/445 | 低頻度・長時間に分散した比較通信 |

### 追加確認が必要な情報

- FILE-SRV-01のアクセスログ
- ファイル監査ログ
- 共有設定
- 対象アカウントの利用履歴
- DEV-PC-03のEDR/OSログ
- 平常時のSMB通信回数・通信量・利用時間帯
- 当該時間帯の業務予定や大量ファイル処理の有無
- バックアップの状態・保全状況

### 軽い解答確認で受講者に確認するポイント

- 「SMB通信が増えた」という通信事実と、「ファイルをコピーした」というホスト側事象を分けているか。
- 比較用SMB通信もあるため、SMBそのものを悪性と決めつけていないか。
- 通信量・頻度・時系列を比較する視点を持てているか。
- ファイルサーバ監査ログと端末ログを追加確認として挙げられているか。

### 議論が脱線した場合の戻し方

- 「SMB通信から直接分かるのは何ですか。」
- 「特定ファイルを操作したと証明するには、何のログが必要ですか。」
- 情報窃取や暗号化の断定に進んだら、ファイル監査・ホスト証跡が不足している点へ戻す。

### 次の状況付与に進むために揃えておきたい認識

- FILE-SRV-01へのSMB通信集中は確認できる。
- ファイル操作の内容と結果は未確認である。
- FILE-SRV-01の監査ログ、対象端末ログ、平常時比較が重要である。

## 7. 状況付与4 模範解答：複数部署からの共有ファイル利用不可報告

### この時点で確認できる事実

- General AffairsとDevelopmentの利用者から、共有フォルダ上の一部ファイルを開けないという申告がある。
- ファイル名や拡張子が通常と異なるという申告もある。
- これは**利用者申告としての事実**であり、原因の技術的確定ではない。
- PCAPでは次の通信が申告前後に観測される。
  - GA-PC-01 → FILE-SRV-01 SMB/445
  - DEV-PC-01 → FILE-SRV-01 SMB/445
  - DEV-PC-03 → GA-PC-01 TCP/445
- 比較用としてIT-PC-01 → AD-SRV-01のDNS通信も存在する。

## 12. 初動対応案

初任者向けの模範としては、次の順序で考えられる。

1. **記録**：観測事実、利用者申告、実施措置、時刻、判断理由を記録する。
2. **証跡保全**：UTM/VPN、AD、FILE-SRV-01、関連端末、ネットワークログを失わないよう保全を依頼する。
3. **影響範囲確認**：通信先、関連端末、利用者申告、重要サービスを整理する。
4. **継続監視**：同一送信元、関連端末、FILE-SRV-01、外部宛通信を継続監視する。
5. **封じ込め検討**：業務影響と証跡保全を考慮し、必要な通信制限・隔離候補を上位者と検討する。
6. **バックアップ保全**：影響拡大の可能性を考慮し、バックアップの状態と保全を確認する。
7. **エスカレーション**：複数の観測事実と業務影響を確度付きで上位者へ共有する。
8. **追加ログ取得後の更新**：仮説を再評価し、断定可能になった事項と未確認事項を更新する。

詳細な復旧方法、攻撃手順の再現、高度フォレンジックは本演習の主対象としない。

- UTM/プロキシ等の外部通信ログ。

### 初動対応案

- 上記ログの保全と取得を優先する。
- 関連端末・重要サーバの監視を継続する。
- 業務影響・証跡保全を踏まえ、必要な隔離・通信制限を上位者と判断する。
- バックアップ保全を確認する。
- 実施措置と時刻を記録する。

### SOC / CSIRT内で共有・エスカレーションすべき内容

- 境界から内部重要サービス、ファイルサーバ、複数端末へ広がる通信事実と業務影響申告。
- 侵入・暗号化・窃取は未確認であり、追加ログが必要であること。
- 証跡保全と封じ込め判断を優先する必要があること。

### 判断理由

- 単一の通信だけではなく、複数の独立した観測事実と利用者影響が時系列で重なっているため。
- 一方で、成功・実行結果を示すホスト側・認証側証跡がまだ不足しているため、確度を分けた報告が必要。

## 15. 初任者が間違えやすい点

| 誤解 | 修正すべき考え方 |
|---|---|
| 外部IPからVPNへ通信があるので侵入成功 | PCAPで言えるのは通信の存在・頻度等まで。認証・侵入はVPNログ等で確認する。 |
| Kerberos/LDAP通信があるので認証成功・管理者権限取得 | プロトコル通信の存在と認証結果・権限付与は別。ADログが必要。 |
| 複数VLANへのTCP/445通信があるので水平展開成功 | 接続範囲は材料になるが、成功には端末・認証・EDR等の追加証跡が必要。 |
| SMB通信量が多いのでファイルコピー・窃取 | 通信量だけでは具体的ファイル操作や送信データの意味を断定できない。 |
| ファイルが開けないので暗号化確定 | 利用者申告は重要だが、ファイル状態・EDR/AV・監査ログで原因確認が必要。 |
| DEV-PC-03から他端末へTCP/445があるのでDEV-PC-03が原因端末 | 通信元であることと侵害起点であることは別。複数ログの突合が必要。 |
| 外部宛HTTPSがあるのでC2・情報窃取 | HTTPS通信の存在は確認できても暗号化された内容や意図は分からない。 |
| 全体がランサムウェアらしいので初動報告で断定してよい | シナリオらしさではなく、証拠ごとの確度を維持して報告する。 |

## 16. 解説時に開示してよい情報と、進行中に直接教えてはいけない情報

### 進行中に直接教えてはいけない情報

- 後続の状況付与内容・順序。
- 「この通信が攻撃通信である」という結論。
- VPN認証成功、侵入成功、脆弱性悪用成功。
- AD認証成功、管理者権限取得、水平展開成功。
- 特定端末が侵害端末・原因端末であるという断定。
- ファイル閲覧・コピー・窃取・暗号化・マルウェア実行の断定。
- 外部HTTPSのC2成立の断定。
- `traffic_id` やfinding IDを受講者に答えとして提示すること。
- 答えに直結するWiresharkフィルタ。

### 全体解説・振り返りで開示してよい情報

- 演習設計上、どの通信を「不審側」「比較側」として配置したか。
- `traffic_plan` とfindingの対応。
- 元の公開報告書から抽出したVPN起点の疑いという要点と、自組織ネットワークへの写像。
- 演習上の仮定として、内部探索・水平展開・ファイル共有周辺の異常を考察させる流れを作ったこと。
- 各PCAP findingの正解。
- ただし、全体解説でも「PCAPが認証成功・暗号化・窃取を証明した」とは説明しない。

## 17. 演習担当者向け最終チェック

- 18件のPCAP findingすべてを、対応する `traffic_id` と関連付けて説明できるか。
- 利用者申告とPCAP証拠を別々に説明できるか。
- 「元報告書の事実」「演習上の仮定」「PCAPで確認できる事実」を区別して説明できるか。
- 受講者の回答が異なっていても、確度の付け方と追加確認の妥当性を評価できるか。
- 組織固有の実運用手順と異なる初動案が出た場合、演習後に人間レビューで調整する前提を維持できるか。
